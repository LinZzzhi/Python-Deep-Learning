### 关键技术结论（踩过的坑）
1. **崩溃：文件未打开时调 `get_pts()` 会段错误（access violation）。**
   ffpyplayer 的 `get_pts()` 会访问 `ivs.ic.start_time`，此时 read 线程还没
   `avformat_open_input`，`ic` 为 NULL。判据：`get_metadata()` 里 `duration` 由
   `None` 变为非 None（core.pyx:2001，在 `self.ic = ic` 之后）即表示文件已打开。
   加了 `_ready` 门控后才允许调用 `get_pts()`。
2. **暂停状态下 seek 不会刷新画面。** `get_frame()` 在 paused 时恒返回
   `(None, 'paused')`；`force_refresh=True` 只重发上一帧。可行做法：临时
   `set_pause(False)` 取到目标帧后再暂停回去（`_scrubbing` 标记）。
3. **seek 后解码器里残留旧帧**，需要用目标 pts 容差丢弃（`_seek_target` / `SEEK_TOLERANCE`）。
   纯音频无帧可丢，不要设置 `_seek_target`，否则会误触发 scrubbing 而变成自动播放。
4. **`canvas.itemconfigure` 报 `image "pyimageNN" doesn't exist`**：先释放
   `self._photo` 引用再操作画面项就会这样。改成先 `image=""` 摘图，最后再丢引用。
5. Tk 8.6 支持 PPM(P6)，`tk.PhotoImage(data=ppm_bytes)` 可直接显示原始 RGB，
   **不需要 Pillow**（base64 方式反而会报错）。视频缩放交给 ffmpeg 的
   `set_size()`（swscale），比 Python 侧缩放高效。
6. 进度/时间用 `get_pts()`（音频主时钟）比视频帧 pts 更准；音频设备启动有约 1s 延迟，
   启动瞬间进度会短暂停在 00:00，属正常。

### 验证方式
写了临时回归脚本（已删），覆盖 mp4(h264+aac) / mp3 / webm(vp9 无音轨) 三种：
播放启动、时长、暂停定位（含暂停态画面刷新）、恢复播放、帧渲染 → 26 项全通过。

### 这轮又踩到的坑
1. **`self._w` 是 Tkinter 保留属性**（控件路径名），当宽度用会把 `self.tk.call`
   搞坏，报 `invalid command name "86"`。改名 `_bw` / `_bh`。
2. **定位后进度/时间会跟画面差好几秒**，根因有两层：
   - 丢旧帧是「一帧挂一个 `after(10)`」，而 Tk 定时器精度约 15ms，队列一积压
     就丢不完、超时停在中间某帧。改成在 `_tick` 里用 while 批量丢（上限 500）。
   - 定位后 ffplay 要用几秒把画面拉回音频主时钟，这期间 **音频时钟会明显落后
     于已显示画面**（实测差约 3s，缓慢收敛）。所以进度不该用 `get_pts()`。
     改成有视频时以「最后显示那一帧的 pts」为准（`_frame_pts`），
     仅在画面已放完但音频还在播时回退到时钟。这样进度条/时间永远和屏幕一致。
3. `tk.PhotoImage(data=ppm_bytes)` 可直接显示原始 RGB（PPM P6），不需要 Pillow；
   base64 反而报错。
4. 截图校验：PowerShell `Add-Type` 被安全策略拦截，改用 Python + Pillow +
   `ctypes.windll.shcore.SetProcessDpiAwareness(2)` + `ImageGrab.grab(bbox)`，
   否则高 DPI 下截出来的窗口会被裁掉一大半。

## 修复用户反馈的两个问题

### 1. 拖放没实现（提示语却写了"拖到这里"）
Tk 没有原生拖放，引入 `tkinterdnd2==0.6.3`（wheel 里自带 tkdnd 2.10.2）
补上，`requirements.txt` 已更新。
- 坑：**`tkinterdnd2._dnd_bind` 故意去掉了 tkinter 标准的 `if {...}=="break"`
  包装**（源码里带 FIXME），所以回调返回值会直接交给 tkdnd，
  **必须返回动作字符串**（`"copy"`），返回 `None` 这次拖放就无效。
  另外 `<<DropEnter>>` / `<<DropPosition>>` 也要绑并返回动作，否则不显示接受光标。
- 坑：Windows 上每个 Tk 控件都是独立 HWND，只在根窗口注册的话，鼠标在画面区/按钮上
  松手接不到。改成递归注册整棵树（15 个控件全覆盖）。
- 窗口标题栏和普通 `tk.Tk()` 不兼容，`main()` 改用 `TkinterDnD.Tk()`，
  装不上则回退 `tk.Tk()`（功能降级为只能用「打开文件」按钮）。
- 验证手段：`ole32.RevokeDragDrop(hwnd)` 返回 `S_OK` 即证明该 HWND 上真的挂了
  OLE `IDropTarget`（未注册的对照控件返回 `DRAGDROP_E_NOTREGISTERED`），
  比"注册没抛异常"可信得多（try/except 会吞掉失败）。

### 2. NVIDIA 4K 录制被识别成音频（用户文件 1.17GB / 3072x1920 / 60fps / 148s）
根因：`get_metadata()['duration']` 是读线程 `stream_open` 阶段填的，而
`src_vid_size` 要等**视频线程解出第一帧**才填，实测差约 100ms（0.22s vs 0.32s）。
原代码一拿到 duration 就断言"没有 src_vid_size → 纯音频"，且不再复查 → 永久误判。
修法：`_apply_metadata` 改成可反复调用的 `_sync_metadata`，只要还没确认有视频就
继续同步、发现视频流就纠正回视频态；"纯音频"要等 1s 观察期（`AUDIO_PROBE_DELAY`）
过了才下结论。实测该 4K 文件现已正确识别并按窗口缩放播放（输出 762x476，11s 渲染 628 帧）。

## SimpleChat 在线聊天室（新建 SimpleChat/，已发布上线）

要求：浏览/搜索房间（显示在线人数、有无密码）、创建房间（生成不重复的 6 位数字密码，
可不设密码，上限 10 人）、加入（列表点击或凭密码）、房主可移人/解散、发布上线。

### 技术选型的关键判断
- **纯标准库后端**（http.server.ThreadingHTTPServer），零第三方依赖 → 部署沙箱
  里不会因为装依赖失败而出问题。入口 `server.py`，监听 `$PORT` 绑 0.0.0.0。
- **前端短轮询（1s）而不是 WebSocket/SSE**：线上是"反向代理 + 单端口"，
  WebSocket 要 Upgrade、SSE 要长连接不缓冲，都取决于代理配置，无法预先验证；
  普通 GET/POST 在任何代理下都通。代价是最多 1s 延迟，对简易聊天室够用。
- 房间/成员/消息全放内存，进程重启即清空（临时聊天室的预期行为）。

### 设计要点
- 成员有两套 id：`token`（会话凭证，只有本人知道，用于鉴权）和 `mid`
  （对外公开，用于"移出成员"），避免把 token 泄露给同房间的人。
- 消息带发送者 `mid`，前端判断"是不是自己发的"用 mid 而不是昵称（昵称可重复）。
- 在线判定：15s 内有轮询即在线；离开时用 `navigator.sendBeacon` 立刻通知，
  不用等超时。空房间 5 分钟后回收，列表只显示有在线成员的房间。
- 创建者权限绑定会话 token，但前端把凭证存 localStorage，再次加入时带
  `resume_token`，服务端校验后转移所有权 → 关掉浏览器回来权限不丢。
- 系统消息（创建/加入/离开/被移出）走同一个消息流，`system: true`。
- 消息渲染全部用 `textContent`，防 XSS（实测 `<b>xss</b>` 会被转义显示）。

### 测试
- 后端 API：42 项（创建/密码唯一性/搜索/三种加入路径/10 人上限/权限/踢人/解散/
  since 增量/参数校验/路径穿越），进程内起服务便于 monkeypatch ONLINE_TIMEOUT。
- 前端 E2E：**用 CDP 直接驱动系统 Chrome（headless）**，双标签页模拟两个用户，
  27 项全过，连跑 3 次稳定。避免了 agent-browser 要下载 500MB Chromium。

### 这轮踩的坑
1. **PowerShell/node 后台进程会随上一条 shell 命令被回收**——测试脚本必须自己
   spawn 服务器，不能依赖上一条命令里 `&` 起的进程。
2. **Chrome CDP 的 `/json/new?<URL>` 必须传原始 URL（PUT）**，`?url=` 或
   encodeURIComponent 过的都不行（会得到 about:blank）。
3. **headless Chrome 自动关闭 confirm/alert（返回 false）**——测试里要
   `window.confirm = () => true`，且必须在 goto 之后设（导航会重置页面上下文）。
4. `window.confirm` 在真实浏览器里没问题，但拦截它之后才能真正走到业务分支。
5. 修了一个真 bug：`_member_public` 给所有成员都写死 `is_you: False`，只有单独

7. `npm install` 前一定确认 `cd` 成功：有一次 cd 失败后 npm 装到了用户工作区根目录，
   污染了目录（已清理）。受管理的 node workspace 目录 `~/.workbuddy/binaries/node/workspace`

## SimpleChat bugfix：自己的消息在自己视角显示两遍

### 根因（纯前端竞态，服务端没问题）
`static/app.js` 允许两个 `/api/rooms/state` 请求同时在飞，且都带着同一个 `since`：
1. 周期轮询 P1 带着 `since=L` 发出，但被网络/代理拖慢；
2. 期间用户发消息落库 → `sendMessage` 完成后 `schedulePoll(0)` 立刻又发一个 P2，仍是 `since=L`；
3. 两个响应先后回来，服务端按 `since=L` 各自返回同一批消息，`renderRoom` 无条件 append → 同一条消息画两遍。
别人的视角只从服务端读到 1 条，所以显示正常 —— 现象与用户描述完全一致。
注：不只是自己的消息，同一窗口内任何消息（含系统消息）都可能被画两遍。

### 修法（app.js）
1. 轮询串行化：`state.pollBusy` 锁 + `state.pollAgain` 补拉标记，新增 `requestPoll(immediate)`
   取代各处 `schedulePoll(0)`；任何时刻只允许一个 state 请求在飞。
2. 渲染幂等：`state.rendered`（Set）记录已画过的消息 id，`lastMsgId` 取返回值最大值而非最后一条。
3. 陈旧响应丢弃：`pollRoom` 开头记下 `owner = state.session`，回来后若 session 已变（换了房间）直接丢弃。
副作用（可接受）：若发送请求时有轮询在飞，自己的消息要等那一轮返回才显示（最坏等一个 RTT）。

### 验证方法（可复用的确定性复现）
Node 写一层 **延迟代理**（只把下一个 `/api/rooms/state` 压 1200ms 再转发），浏览器经
`--proxy-server` + `--proxy-bypass-list=<-loopback>` 走代理，页面里手动 `pollRoom()`
造出飞行中的请求，紧接着发消息 → 稳定复现 2 条。修复后同一脚本 26 项回归全绿，
`State 请求并发度恒为 1`。测试脚本在 `%TEMP%/sc-dup-test/`（repro.js / regression.js）。
修复已重新发布：同一链接 https://simple-chat-room.app.workbuddy.host/ ，
用 `curl .../app.js` 核对线上字节数与本地一致（16417，含 pollBusy）确认生效。
线上静态资源挂在根路径（/app.js），**不是** /static/app.js。

## SimpleChat 第二轮：两个 bug + 管理员功能

### bug1：进房间后刷新浏览器被踢回大厅
根因：`app.js` 的 `beforeunload` 里用 `sendBeacon` 主动调 `/api/rooms/leave`，
刷新时先把成员删掉，重新加载后 `resumeSession` 拿到 `removed` → 踢回大厅。
**"主动下线"与"刷新恢复会话"天然互斥**。
修法：删掉 beforeunload 的 leave（保留「离开」按钮的 beacon），在线状态交给
服务端 15 秒轮询心跳自然收敛。代价：关掉页面后最长 15 秒才从在线列表消失。

### bug2：连击「创建并进入」造出多个同名僵尸房
根因：`createRoom()` 没有在途锁，每次点击都发一个 POST。僵尸房靠 `_online()` 过滤，
约 15 秒后才从大厅消失（但仍在内存里），所以表现为"解散真房间后一起消失"。
修法：`state.createBusy` + 按钮 disabled（`setBusy()`），加入按钮同理 `joinBusy`。
验证：代理侧统计 POST /api/rooms 次数 === 1。

### 新增：管理员（昵称 admin）
- 服务端：`/api/admin/login|update|ghost|data`；`Member` 加 `ip/ghost/admin`；
  `Room` 加 `owner_name/participants/ended`；`_online()` 默认排除无痕成员；
  `_can_manage()` = 房主 or 管理员。
- IP 采集：优先 `X-Forwarded-For` → `X-Real-IP` → socket 地址；消息与成员都记 IP，
  但**只在管理员视角下发**（普通用户的消息对象里没有 ip 字段）。
- 无痕加入：不校验密码、不占人数上限、不计在线人数、不发加入/离开系统消息，
  但拥有房主权限（移出成员、解散房间）；无痕成员对普通用户完全不可见。
- 历史：`_history` 保存已解散/已回收房间的快照（参与者用户名+IP+加入/离开时间、
  全部消息含 IP），上限 100 条；活跃房间实时快照，管理员看到的是两者合并。
- 账号持久化：`admin.json`（沙箱不可写时退化为内存态）；密码默认 12345678。
- 前端：昵称是 admin → 弹 `type=password` 模态框（默认填 12345678）→ 管理员控制台；
  可改用户名/密码（显示/隐藏切换，接口把当前密码回传给已登录管理员以便明文查看）；
  房间列表支持无痕加入；房间内成员列表显示 IP；历史房间用 `<details>` 展开看参与者与消息表。
